# 本地 JSON 数据恢复

本说明适用于单进程使用的 `CG_DATA_DIR`，默认是项目根目录 `.data`。不要让两个服务同时使用同一目录。

## 发现损坏时

主文件不是有效 JSON 或缺少必要结构时，API 返回 `STORAGE_CORRUPT` / HTTP 503。健康检查逐项列出 workspace、connections、agents、connectionTests。前三项故障返回 503，并保留服务身份，便于启动器核验停止请求；仅连接测试日志故障时返回 200 + degraded，设置页显示告警，主流程仍可用。程序不会用示例、缓存或备份自动覆盖主文件。

1. 停止使用该目录的服务。启动器启动的实例使用 `node scripts/stop.mjs`；终端启动的实例在对应终端按 Ctrl+C。确认进程退出后再处理文件。
2. 将整个数据目录复制到独立备份目录，保留损坏主文件、`.bak`、旧迁移备份和可能残留的 `.tmp`。备份可能包含正文和明文 API 密钥，按私密文件保管。
3. 核对出错文件及同名 `.bak` 的修改时间、JSON 是否可解析和业务内容，例如项目数、版本、最近运行、模型连接。JSON 可解析只是必要条件，不能证明内容完整。
4. 选择已核对的备份，先复制到一个新的测试数据目录，用独立端口启动检查。不要让测试实例调用真实付费模型。确认内容后，保持正式服务停止，将损坏主文件另名保留，再以选定备份恢复该文件。
5. 重新启动正式服务，检查健康状态、版本和历史。恢复会回退到所选备份时间；备份之后的修订、调用和费用记录可能缺失，需要保留原文件供人工核对。

没有可用备份时应保留原文件，先进行人工数据修复；删除文件会触发初始化，不能视为恢复成功。

## 检查点的实际范围

发生有效变更的事务提交前，最多每分钟复制一次当前可读文件到 `<文件名>.bak`。空事务不会更新主文件或检查点。检查点是单份轮换，首次写入、进程重启后的第一次有效变更可能立即生成，长期没有变更时也可能较旧；它不是完整版本备份。

复制检查点本身没有断电持久保证。主文件使用同目录临时文件与原子替换，遇到暂时占用会短暂重试；仍未实现 fsync 或多进程事务锁。断电、磁盘故障和外部文件改写后的无损恢复不在保证范围内。请另外定期备份整个数据目录。

## 启动记录

新启动器在 Windows/Linux 尝试记录进程创建身份及程序路径，用于识别 PID 复用；身份无法读取、旧记录缺少身份或其他平台时采取保守处理，可能仍要求人工核对。停止服务继续使用实例、PID 和私密令牌校验，不向不明 PID 发送终止信号。

## 四类文件的处理范围

- `workspace.json`：项目主数据；事务检查点为 `workspace.json.bak`。
- `agent-jobs.json`：协作记录；事务检查点为 `agent-jobs.json.bak`。损坏不会影响项目正文读取，但协作接口返回 503。
- `connections.json`：连接与明文密钥；校验 JSON 及配置结构。旧版迁移备份位于 `backups/connections-v1.json`，不是日常轮换备份。
- `connection-tests.json`：辅助测试日志；损坏时不覆盖、不自动重建，设置页提示。连接测试仍能返回本次结果、用量与日志未保存告警，请人工保留；失败测试仍返回原调用错误。

仅前两项通过 JSON 事务生成每分钟检查点；其余文件需依靠整个数据目录的人工备份。检查点复制失败会以 CHECKPOINT_FAILED 告警（只含文件名与系统错误代码），继续尝试主文件原子提交；主文件提交失败仍报错，绝不假报保存成功。
