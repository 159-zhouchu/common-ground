## 发布前需处理

1. **确定并添加 LICENSE。** 根目录没有 LICENSE，package.json 也没有 license 字段。公开可见不等于授予他人使用、修改和再分发的开源许可。若希望宽松复用，可考虑 MIT；若重视明确的专利授权条款，可考虑 Apache-2.0。最终选择由权利人决定，作者署名和年份应真实，不能替其他贡献者授权。
2. **整理公开范围。** 不要上传整个本机工作目录。保留源码、测试、启动脚本、锁文件及必要说明，排除真实 .data、.env、node_modules、.next、qa、日志、桌面配置和个人工具目录。当前 .gitignore 已覆盖主要业务私有数据，但尚未覆盖 .codex、desktop.ini 等本机杂项。docs/evidence 应逐项选择：本次未发现真实密钥，但部分原始日志含开发机路径，且没有必要全部进入公开仓库。
3. **修正面向公众的说明。** docs/Agent接入.md 第 39、51 行使用开发者电脑的绝对路径，应改为用户实际克隆目录的示例。docs/验证记录.md 第 61 行链接的 app/ambient.tsx 已删除，应注明历史记录或修正链接。README 首部应便于陌生用户找到用途、安装、启动与限制。

## 第三方许可与素材

锁文件依赖并非全部 MIT：包含 ISC、BSD、Apache、CC-BY，以及 sharp/libvips 可选平台二进制涉及的 LGPL 声明。JSZip 的 MIT OR GPL 允许选择 MIT；不能据此断言整个项目必须 GPL，也不能将自己的 LICENSE 当作所有第三方代码的许可。

建议生成第三方依赖许可及归属清单，分发依赖或平台二进制时按实际许可履行相应要求。当前源码分享包不含 node_modules 或构建产物。应用未发现随包字体文件或第三方图片；这不替代所有贡献者对原创代码和素材来源的确认。旁边的宣传片工程不属于本次源码发布范围。

## 建议补充，非全部为发布硬门槛

- 增加 CI，至少运行安装、类型检查、测试与构建；声明实际验证的 Node 与操作系统。
- 增加 SECURITY.md 和简短 CONTRIBUTING.md，提供漏洞反馈方式、贡献及模拟测试要求。
- 保留本地单用户定位：密钥在本地明文保存，没有公网多用户认证与隔离，不应宣传为可直接公网部署的服务。
- 清楚区分 Windows 实测、Linux/macOS 未原生复测，以及模拟供应商通过、真实付费模型未验证。

package.json 的 private: true 仅阻止误发 npm，不妨碍 GitHub 开源，无须为开源而删除。

建议先发布为 0.1.x 早期版本，完成许可与公开范围整理后，再从干净导出目录安装、构建并核对一次发布包。不要把“开源可用”表述为“完美、无漏洞或全平台验证通过”。
